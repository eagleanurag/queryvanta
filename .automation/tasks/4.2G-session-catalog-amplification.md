## Objective

See the title and the audit sections above. State the goal in one sentence in
your own words before making any change.

## Scope

Two self-inflicted costs remain: a session read is a write, and each admin
mutation triggers several identical full-catalog fetches.

Reduce both.

## Scope
1. Stop updating the session last-seen timestamp on every read. Update it only
   when it is older than a threshold, or fold it into periodic housekeeping.
2. Stop re-fetching the whole admin catalog several times per mutation. Prefer
   returning the mutated row and updating local state from it.

## Non-goals
No schema change unless the threshold approach proves one is needed, and say so.
No change to session expiry, revocation, hashing, cookie attributes, or the idle
timeout semantics. Do not weaken the idle timeout: a longer effective timeout is
a security regression. Do not change which operations refresh the session.

## Implementation requirements
Read the audit rows above and the existing client sync code before designing this.
The idle-timeout behaviour is a security control, not a convenience: whatever
threshold you introduce must not let a session live longer in practice than the
documented idle TTL. The client change is the more delicate half: the admin list
must stay correct after create, update, delete, publish, unpublish, enable,
disable and duplicate, and must still recover correctly on a full page refresh.

## Required tests
- A session read no longer writes on every request.
- Idle timeout is still enforced at the documented interval.
- One admin create issues one catalog fetch, not three or four.
- The admin list is still correct after every mutation listed above.
- A full page refresh still reloads the catalog from the server.
- All 133 server tests and the existing admin browser suites still pass.

## Completion criteria

admin list is demonstrably correct after every mutation, and every gate passes

## Stop conditions
