# Task 4.2A — Move housekeeping off the request path and add scheduled retention

- **Roadmap id:** `4.2A`
- **Phase:** Phase 4 - free-tier and abuse hardening
- **Position:** 1 of 14
- **AUTO_COMMIT:** false
- **AUTO_PUSH:** false
- **Approved input:** `docs/qa/phase-4-abuse-audit.md`
- **Audit sections to read:** D (rows V-03, V-09, V-13), F, J, K step 1

---

## Objective

Remove D1 write amplification from the hottest anonymous endpoint, and give
housekeeping a reliable home that does not depend on a user visiting a page.

Concretely: stop performing session and OAuth-transaction purges inside the
request path, run them from a Worker scheduled trigger instead, and add a
bounded retention policy for the audit log so it cannot grow without limit.

## Scope

1. **Remove request-path housekeeping.**
   `server/index.ts` currently runs two D1 `DELETE` statements in a `finally`
   block via `ctx.waitUntil()` whenever the pathname starts with
   `/api/auth/session`. Remove that block entirely.

2. **Add a scheduled handler.**
   Add a `scheduled()` export to the Worker default export object in
   `server/index.ts` that runs:
   - `purgeExpiredSessions` (already exported from `server/session.ts`)
   - `purgeExpiredOAuthTransactions` (already exported from `server/oauth.ts`)
   - a new audit-log retention delete

   Both existing purge helpers are already implemented and already exercised by
   tests; reuse them rather than writing new logic.

3. **Add a cron trigger.**
   Add a `[triggers]` section with a `crons` entry to `wrangler.jsonc`. Choose a
   schedule that is off-peak for the deployment region and infrequent enough to
   be cheap. Daily is almost certainly sufficient; justify whatever you choose in
   the summary.

4. **Add audit-log retention.**
   Introduce a bounded retention window for `admin_audit_log`. Use a
   parameterised `DELETE` with a timestamp cutoff. `admin_audit_log` already has
   an index on `created_at DESC`, so a time-windowed delete uses the existing
   index — **no schema change is required and none is permitted.**

   Put the retention period in `wrangler.jsonc` `vars` (for example
   `AUDIT_RETENTION_DAYS`) so it is configuration, not a magic number, and so it
   can be read through the existing `Env` type. Add the field to the `Env` type
   in `server/env.ts` with a comment explaining it is not a secret.

5. **Test it.**

## Explicit non-goals

- No D1 schema change. No new table, column or index.
- No rate limiting. That is task 4.2B.
- No change to the OAuth start route. That is task 4.2C.
- No caching or ETag changes. That is task 4.2D.
- No change to the public list query or its filters. That is task 4.2E.
- No change to the import path. That is task 4.2F.
- No change to the session lookup write behaviour. That is task 4.2G.
- Do not change the security model. Sessions stay hashed, opaque,
  server-verified, HttpOnly, SameSite, and expiry stays enforced on every read.
- No production deployment. No remote D1 command. No secret or credential
  change.
- Do not "improve" anything you notice that is not listed above. Report it
  instead.

## Relevant existing audit findings

- **V-03** — `GET /api/auth/session` is unauthenticated and triggers two D1
  `DELETE` statements per call through `ctx.waitUntil()`, plus one `SELECT` in
  `lookupSession()`. Roughly three D1 operations per request, repeatable by
  anyone at no cost to the caller.
- **V-13** — there is no cron or scheduled handler anywhere in `server/**`;
  housekeeping only ever runs opportunistically on that one endpoint.
- **V-09** — `admin_audit_log` has no retention policy at all, and the purge
  helpers cover only sessions and OAuth transactions.

## Implementation requirements

1. Keep the existing exported purge functions and their signatures. Reuse them.
2. The scheduled handler must not throw the whole invocation if one purge
   fails. Isolate each purge so one failure does not prevent the others. Use
   `Promise.allSettled` or equivalent and log failures.
3. The retention delete must be parameterised. No string interpolation of a
   value into SQL anywhere in this repository.
4. The retention window must be validated at read time: a missing, zero,
   negative or non-numeric value must fall back to a documented safe default
   rather than deleting everything or nothing.
5. Removing the `finally` block must not change any response. `/api/auth/session`
   must return exactly what it returned before, with the same status, body and
   headers.
6. `purgeExpiredSessions` and `purgeExpiredOAuthTransactions` must remain
   exported and must remain referenced, so they do not become dead code.
7. Add a comment in `wrangler.jsonc` explaining the cron schedule choice.
8. Do not add a `console.log` on a hot path. The scheduled handler may log a
   short summary line.

## Required tests

Add to `server/tests/security.test.ts` or a new focused test file alongside the
other server tests.

1. `GET /api/auth/session` performs **no** D1 write. Assert this by checking D1
   state directly through the test harness: call the endpoint and confirm
   `last_seen_at` and the row counts are unchanged, and that expired rows are
   still present afterwards.
2. `/api/auth/session` still returns the same envelope, status and headers as
   before for both the authenticated and unauthenticated cases.
3. Invoking the scheduled handler removes expired sessions.
4. Invoking the scheduled handler removes expired and already-consumed OAuth
   transactions.
5. Invoking the scheduled handler removes audit rows older than the retention
   window and keeps rows inside it.
6. A missing or invalid `AUDIT_RETENTION_DAYS` falls back to the documented
   default and does not delete recent rows.
7. A failure in one purge does not prevent the other purges from running.
8. All 50 pre-existing tests in `server/tests/security.test.ts` still pass
   unchanged. If one of them needs adjusting because behaviour genuinely
   changed, say so explicitly in the summary and explain why.

The existing test harness (`server/tests/harness.ts`) already boots a real
Worker against a local D1 and exposes a D1 command helper. Use it rather than
inventing a new harness.

## Completion criteria

- The `finally` block in `server/index.ts` that performed the purges is gone.
- The Worker exports a `scheduled()` handler that runs both existing purges plus
  audit retention.
- `wrangler.jsonc` declares a cron trigger with an explanatory comment.
- The retention window is configuration in `wrangler.jsonc` vars, declared on
  the `Env` type, with a documented fallback.
- No D1 schema change.
- All required tests exist and pass.
- All quality gates pass, with observed output.
- No unrelated file was modified.

## Stop conditions

Stop and report `BLOCKED` if any of these turn out to be true:

- Audit retention appears to require a schema change or a new index.
- The scheduled handler cannot be added without changing the Worker entry
  point's existing `fetch` contract.
- `purgeExpiredSessions` or `purgeExpiredOAuthTransactions` turn out to be
  unusable from a scheduled context.
- The existing test suite cannot be run in this environment.
- Any required gate fails and you cannot fix it within scope.
- The task turns out to require a production deployment to validate.
