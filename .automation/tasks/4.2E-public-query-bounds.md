## Objective

See the title and the audit sections above. State the goal in one sentence in
your own words before making any change.

## Scope

The public list query has no limit and its filters are unvalidated.

Bound both.

## Scope
1. Add a bounded result limit to the public list query.
2. Validate the three filter values against an allow-list with a length cap.
3. Make the response honest about what was returned when a limit applies.

## Non-goals
No caching (4.2D). No schema change: the existing indexes already support the
query and its ordering. Do not change the public visibility predicate. Do not
change the admin list, which the audit did not flag for bounding. Do not remove a
filter to "fix" the problem.

## Implementation requirements
Decide the limit and the allow-list from the actual data: read
`src/data/questions.ts` and the question schema to find the real values of
question type, category and difficulty rather than guessing. Return a total count
alongside the page so the client can still show an accurate number. Reject
out-of-range filter values with a clear client error rather than silently
returning nothing, so the behaviour is discoverable.

## Required tests
- The public list honours its limit and reports the total separately.
- A filter value outside the allow-list is rejected with a client error.
- An over-long filter value is rejected.
- Valid filters still work, including combined filters.
- The 50 pre-existing security tests still pass.
